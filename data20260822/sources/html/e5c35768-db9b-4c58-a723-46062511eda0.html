Ubuntu 20.04 部署 K8S 1.27
一、K8S 架构
Kubernetes（简称 K8S）是一个开源的容器编排平台，用于自动化部署、扩展和管理容器化应用程序。
K8S 的架构分为以下几个组件：
- Master（Control Pannel）节点：K8S 集群的控制中心，负责管理整个集群的状态和控制应用程序的部署、升级和伸缩等操作。Master节点包括以下组件：
- kube-apiserver：提供 K8S API，处理 REST 请求并验证和授权用户的请求。
- etcd：分布式键值存储，用于存储 K8S 集群的配置信息和状态信息。
- kube-scheduler：负责监视新创建的 Pod，并将其分配给合适的 Node 上运行。
- kube-controller-manager：负责管理集群级别的控制器，如节点控制器、副本控制器、服务控制器等。
- Node节点：K8S 集群中的工作节点，负责运行容器应用程序。Node节点包括以下组件：
- kubelet：负责管理 Node 上的容器，包括启动、停止、监控和报告容器状态等。
- kube-proxy：负责实现 K8S Service 的网络代理和负载均衡功能。
- 容器引擎：负责运行容器应用程序的软件环境，如 Docker、containerd、rkt、podman等。
K8S 的部署要求如下：
- 操作系统：K8S 支持多种操作系统，包括 Linux、Windows 和 macOS 等。
- 硬件资源：K8S 除支持 x86 架构服务器，还支持 ARM 架构服务器，甚至包括国产龙芯架构服务器。
- 服务器数量：为保证高可用性，K8S 要求至少 3 台服务器， 1 个 Master 节点，2 个 Node 节点。如果仅是测试用途，也可只使用 1 台服务器部署 1 个 Master 节点，通过移除污点也可以部署应用容器。
- 网络环境：K8S 要求 Master 和 Node节点之间网络互通。
- 容器引擎时：K8S 目前支持 Docker、 containerd、rkt、podman 等。
- 容器镜像仓库：K8S 需要一个容器镜像仓库来存储和管理容器镜像。常用的容器镜像仓库包括 Docker Hub、Google Container Registry、AWS Elastic Container Registry 等。
二、相关概念
Kubernetes（简称 K8S）是一个庞大的容器编排平台，其中涉及到了许多概念和名词。以下是这些概念和名词的详细介绍和解释：
1. Pod
- 一个或多个容器的集合，是 K8S 部署和调度的最小单位。
- Pod 中的容器共享网络和存储空间，可以通过 localhost 相互通信。
2. Deployment
- 用于管理 Pod 的创建、更新和删除等操作，保证应用程序的可用性和稳定性。
- Deployment 通过 ReplicaSet 控制 Pod 的数量，并支持滚动更新和回滚等操作。
3. Service
- 用于将一组 Pod 暴露为一个稳定的网络端点，提供负载均衡和服务发现等功能。
- Service 通过 LabelSelector 选择一组 Pod，并为其分配一个唯一的 IP 地址。
4. Cluster Network
-一组逻辑或物理的网络连接，用于 K8S 集群中实现网络通讯。
5. Namespace
- 用于将 K8S 集群中的资源划分为多个虚拟集群，实现资源隔离和命名空间隔离。
- Namespace 可以包含 Pod、Service、Volume、ConfigMap 等资源。
6. ConfigMap
- 用于存储应用程序的配置信息，可以在容器中作为环境变量或文件挂载使用。
- ConfigMap 可以通过 kubectl create configmap 命令创建，也可以通过 YAML 文件定义。
7. Secret
- 用于存储应用程序的敏感信息，如密码、证书等，可以在容器中作为环境变量或文件挂载使用。
- Secret 可以通过 kubectl create secret 命令创建，也可以通过 YAML 文件定义。
8. Volume
- 用于将持久化存储挂载到容器中，支持多种存储类型，如本地磁盘、网络存储、云存储等。
- Volume 可以作为容器的文件系统使用，支持读写、只读等模式。
9. Node
- K8S 集群中的工作节点，运行着 Pod，并提供计算和存储资源。
- Node 可以是物理机或虚拟机，需要安装 Docker 或其他容器运行时。
10. Master
- K8S 集群的控制节点，管理着整个集群的状态和控制应用程序的部署、升级和伸缩等操作。
- Master 包括 kube-apiserver、etcd、kube-scheduler、kube-controller-manager 等组件。
11. Ingress
- 用于将外部流量路由到 K8S 集群内部的 Service 上，支持负载均衡、HTTPS、域名解析等功能。
- Ingress 可以通过 YAML 文件定义，并需要安装 Ingress Controller 才能生效。
三、容器引擎
早期 k8s 版本直接将 docker 作为容器引擎，但是之后希望 k8s 可以集成其他容器引擎时，CRI 规范被设计出来用于满足与各种容器引擎进行交互。
但是 docker 在 CRI 规范出现前就已经存在，因此为了保证兼容性，dockershim 适配器被添加进来作为 docker 与 CRI 交互的一个中间层。
而在 1.24 之后的版本，k8s 默认集成 containerd 作为容器引擎，不再需要通过 dockershim 作为中间层，所以调用链更短，组件更少，更稳定，占用节点资源更少。
由于使用 containerd 容器引擎，其默认存储位置在 /var/lib/containerd 目录，socket 位于
/run/containerd/containerd.sock ，使用 crt 和 crictl 命令对镜像和容器进行管理。
使用 crictl 命令前，需要使用下列命令配置 socket 接口，
crictl config runtime-endpoint unix:///run/containerd/containerd.sock
crictl config image-endpoint unix:///run/containerd/containerd.sock

2. Cgroup 控制组
Cgroup 控制组用于限制容器使用的系统资源，如 cpu 和内存。
K8S 默认集成 cgroupfs 驱动作为 cgroup 控制组，但是在目前 Linux 系统均使用 systemd 机制进行初始化。Systemd 与 cgroup 控制组紧密结合，会为每个 systemd 单元（系统服务）分配一个控制组，。如果 systemd 和 cgroupfs 控制组同时使用，系统将会存在两种 cgroup 控制组，cgroupfs 控制容器的资源使用限制，而 systemd cgroup 将会控制系统中其他进程的资源使用限制，因此系统资源限制将变得不稳定，特别是在大压力环境下。
所以，在使用 systemd 初始化机制的操作系统中，K8S 应该使用 systemd 控制组。
为使用 systemd 控制组，需要在 kubeadm 配置 K8S 时指定 cgroup 驱动为 systemd。自 K8S 1.22 开始默认即使用 systemd 控制组。
K8S 所使用容器引擎应与 K8S 使用的 cgroup 控制组保持一致。如使用 containerd 做为容器引擎，则需要在 /etc/containerd/config.toml 配置文件中设置控制组
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc]
...
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
SystemdCgroup = true
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc]
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
BinaryName = "runc"
3. 网络插件
K8S 网络插件有多种，每种插件都有其优点和缺点。以下是几种常见的网络插件及其特点：
3.1. Flannel
- 优点：简单易用，适用于任何环境，性能较好。
- 缺点：不支持网络策略，不适合需要网络隔离的场景。
3.2. Calico
- 优点：支持网络策略和安全策略，性能较好。
- 缺点：配置较为复杂，需要额外的组件支持。
3.3. Weave Net
- 优点：支持多种网络模型，易于部署和管理。
- 缺点：性能较差，不适合高负载场景。
3.4. Cilium
- 优点：支持网络策略和安全策略，性能较好。
- 缺点：需要额外的组件支持，不适合小规模部署。
3.5. Canal
- 优点：结合了 Flannel 和 Calico 的优点，支持网络策略和安全策略。
- 缺点：配置较为复杂，需要额外的组件支持。
选择哪种网络插件取决于具体的需求和场景。如果需要简单易用的网络插件，可以选择 Flannel；如果需要支持网络策略和安全策略的网络插件，可以选择 Calico 或 Cilium；如果需要结合多种优点的网络插件，可以选择 Canal。

5.移除污点
K8S 集群至少需要 1 个 MASTER 节点和 1 个 NODE 节点，MASTER 节点上无法运行用户应用 POD。为避免 POD 被调度到 MASTER 节点，MASTER 节点被标记为有污点。
为了方便单机测试，通过移除 MASTER 节点上的污点，可以让 MASTER 节点可以运行用户应用 POD。
执行 kubectl get no -o yaml | grep taint -A 5 命令检查 master 节点所有的污点；执行 kubectl taint nodes --all node-role.kubernetes.io/control-plane- 命令移除污点。

八、YAML 部署应用
使用 YAML 配置文件部署应用需要执行以下几个步骤：
1.编写应用部署 YAML 配置文件
创建一个包含应用配置的 YAML 文件，文件内容包括：应用程序名，所使用的容器镜像，应用所使用的端口等。
例如，下面是 portainer 部署的 YAML 文件
apiVersion: apps/v1
kind: Deployment
metadata:
name: portainer
namespace: portainer
labels:
io.portainer.kubernetes.application.stack: portainer
app.kubernetes.io/name: portainer
app.kubernetes.io/instance: portainer
app.kubernetes.io/version: "ce-latest-ee-2.18.3"
spec:
replicas: 1
strategy:
type: "Recreate"
selector:
matchLabels:
app.kubernetes.io/name: portainer
app.kubernetes.io/instance: portainer
template:
metadata:
labels:
app.kubernetes.io/name: portainer
app.kubernetes.io/instance: portainer
spec:
nodeSelector:
{}
serviceAccountName: portainer-sa-clusteradmin
volumes:
- name: "data"
persistentVolumeClaim:
claimName: portainer
containers:
- name: portainer
image: "portainer/portainer-ce:2.18.3"
imagePullPolicy: Always
args:
- '--tunnel-port=30776'
volumeMounts:
- name: data
mountPath: /data
ports:
- name: http
containerPort: 9000
protocol: TCP
- name: https
containerPort: 9443
protocol: TCP
- name: tcp-edge
containerPort: 8000
protocol: TCP
livenessProbe:
httpGet:
path: /
port: 9443
scheme: HTTPS
readinessProbe:
httpGet:
path: /
port: 9443
scheme: HTTPS
resources:
{}
- apiVersion：指定要使用的 Kubernetes API 版本。
- kind：指定 Kubernetes 对象的类型，Deployment 表示部署应用。
- metadata：指定对象的元数据，例如名称、标签等。
- name：指定应用名。
- spec：指定对象的规范，例如容器镜像、副本数、端口映射等。
- replicas：指定要创建的 Pod 的副本数。
- selector：指定要选择哪些 Pod 进行操作。
- template：指定要创建的 Pod 的模板。
- nodeSelector: 指定容器运行在哪个节点上。
- containers：指定 Pod 中要运行的容器。
- name：指定容器的名称。
- image：指定要使用的容器镜像。
- imagePullPolicy: 指定容器镜像拉取的策略，always 表示总是从仓库拉取，never 表示不从仓库拉取，IfNotPresent 表示如果本地不存在时从仓库拉取。
- volumeMounts：指定容器挂载的存储或文件。
- ports：指定容器中要暴露的端口。
- containerPort：指定容器中要暴露的端口号。
- livenessProbe: 指定检测 pod 健康的方法。
- readinessProbe: 指定检测 pod 是否已经准备好接受访问。通过适当配置 readinessProbe 和 livenessProbe，可以确保在其他 Pod 可访问之前，Pod 已经准备好接收流量，并保持运行状态。这样可以避免在尚未完全启动或出现故障的情况下将流量发送到该 Pod。
2.编写端口映射 YAML 配置文件
创建一个包含服务配置的 YAML 文件，内容包括对应的 pod，映射的端口和协议。
例如，下面是映射 portainer 端口的配置文件
apiVersion: v1
kind: Service
metadata:
name: portainer
namespace: portainer
labels:
io.portainer.kubernetes.application.stack: portainer

-kind：指定 Kubernetes 对象的类型，例如 Service。
-apiVersion：指定要使用的 Kubernetes API 版本。
-metadata：指定对象的元数据，例如名称、标签等。
-spec：指定对象的规范，例如端口映射、选择器等。
-selector：指定端口映射针对哪些 Pod 进行操作。
-types：指定端口映射的类型，有三种类型：ClusterIP、NodePort 和 LoadBalancer。ClusterIP：为 Service 对象创建一个虚拟 IP 地址，用于在集群内部的其他对象之间路由流量；NodePort：在每个节点上公开一个端口，以便可以通过节点的 IP 地址和该端口访问 Service 对象；LoadBalancer：在云提供商中自动创建一个负载均衡器，并将流量路由到
Service 对象。
-ports：指定要暴露的端口和协议。
-port：指定容器的端口。
-targetPort：指定集群内部容器通讯的端口。
-nodePort：指定集群节点开放大的端口，范围 30000-32767。
3.创建命名空间
kubectl create namespace xxx
4.部署应用
部署应用和映射端口执行 kubectl apply -f xxx.yaml 命令
删除应用和映射端口执行 kubectl delete -f xxx.yaml 命令
5.查看应用状态
查看应用运行状态执行 kubectl get pods -A 命令
查看应用运行问题执行 kubectl describe pod xxx -n xxx 命令
6.调整 POD 配置
编辑命令 kubectl edit pod xxx -n xxx，编辑完成后需要重启 pod
