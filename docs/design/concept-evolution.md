# 概念演化

领域下的概念不是导入时一次性定好的，也不是永远不变的。

概念是认知入口：ActivationLink 挂在概念上，KPP 挂在 Domain / Concept 上，Wiki 概念页围绕概念编译。入口划分得不对，会持续影响激活质量——缺一个概念，一批知识点永远只能靠补充查找兜底；两个概念边界重叠，同类问题在两个入口间摇摆，激活路径无法稳定。

因此，概念需要在使用中演化：新增、合并、拆分。本文档定义这套机制。

可以概括为：

```text
候选来自使用中的信号累积；
候选不参与激活；
晋升和合并永远需要人工确认；
执行时挂载的一切随概念迁移，历史可追溯。
```

## 1. 概念从哪里来

稳定概念有两个来源：

```text
预制：preset/domains.json 中人工维护的领域和概念，启动时写入；
演化：使用中由 Study 观察信号、形成候选、经人工确认晋升。
```

导入阶段最多只能形成候选概念或匹配已有概念（见 `precompile.md` 第 7 节）。概念演化不发生在导入期，只发生在使用后的 Study 环节。

## 2. 演化信号从哪里获取

演化信号有三个产生点，全部依据程序可观察的事实，不依赖模型自评，也不增加模型调用。

### 产生点 1：Concept 匹配阶段（在线）

问题理解时，Concept 匹配器本来就要为每个候选概念计算匹配分。当前两名概念的分数差小于阈值时，匹配器顺手记录一条 `entry_boundary_signal`（子类型 `ambiguous_match`），携带：

```text
两个概念的 ID 与各自匹配分；
本次问题的 scene / goal。
```

这是"摇摆命中"的事实记录，是合并信号的在线来源。

### 产生点 2：采用结果回写阶段（在线）

回答完成后，系统本来就要回写"哪些 KnowledgePoint 被实际采用"（`activation_success` / `activation_gap` 产生于此）。此处的程序判断是：对照被采用 KP 与本次命中概念、链接的挂载关系——

```text
概念匹配成功，KP 挂在该概念的链接下
    → activation_success（与概念演化无关）；
概念匹配成功，但 KP 靠补充查找进入
    → activation_gap，gap_level = link_gap（缺链接，走候选 ActivationLink）；
概念匹配整体失败，KP 全靠目录 / FTS 兜底
    → activation_gap，gap_level = entry_gap（缺概念，本文档的原料）。
```

`gap_level` 的定义见 `trace.md` 第 3 节。区分两级缺口是关键：缺链接说明入口存在、路径未建；缺概念说明入口本身不存在。

### 产生点 3：Study 离线统计（无在线事件）

两类信号本质是统计量，不需要在线记录，Study 周期任务直接从已有数据计算：

```text
概念对的链接重叠度：两概念的 ActivationLink 指向 KP 集合的重叠比例
  （查链接表即可，合并信号的离线来源）；
概念内的事件分布：同一概念下累积事件的 scene / goal 分布
  （查历史事件即可，拆分信号的来源）。
```

## 3. 事件如何触发演化：聚合规则

Study 在周期任务中消费上述信号，形成候选。所有阈值可配置，单次事件不形成候选。

### 新增候选

对窗口内 `gap_level = entry_gap` 的事件，按"同一 Domain + 采用 KP 集合重叠 + scene / goal 相似"聚类。某个簇满足全部条件时形成新增候选：

```text
簇内事件数 ≥ N；
来自 ≥ M 个不同问题（避免同一问题反复提问刷量）；
KP 集合已稳定：新事件不再大幅扩大集合。
```

建议名称从簇内 KP 所属知识单元的高频术语提取，人工确认时可修改。

### 合并候选

两个条件必须同时满足：

```text
同一概念对的 ambiguous_match 累计 ≥ N 次（在线摇摆事实）；
两概念链接指向 KP 集合的重叠度 ≥ 阈值（离线统计）。
```

只有摇摆没有重叠，可能是问题本身表述模糊；只有重叠没有摇摆，可能是正常的邻近概念。单一条件不触发。

### 拆分候选

同一概念下的累积事件在 scene / goal 上分裂为两簇，且两簇采用的 KP 集合基本不相交时，形成拆分候选，附带建议的簇划分。

### 候选的内容与约束

候选应携带完整依据，供人工确认时审阅：

```text
建议名称与建议归属 Domain（新增）/ 涉及概念对与重叠度（合并）/
  建议簇划分（拆分）；
关联的 KnowledgePoint 集合；
观察到的场景、目标分布；
支撑它的全部 Learning Event 列表（可追溯）。
```

候选概念的约束：

```text
候选不参与 Domain / Concept 匹配，不参与正式召回和激活；
候选形成后继续累积：新事件支撑则置信上升，
  长期无新事件则自然过期淘汰。
```

## 4. 晋升与合并需要人工确认

概念是结构性对象，动它会波及 ActivationLink 挂载、KPP 挂载和 Wiki 页面，影响面与 Wiki 编译同级。与「Wiki 编译不全自动」保持同一立场：

```text
候选识别是自动的（Study 聚类并给出依据）；
晋升、合并、拆分的执行永远需要人工确认后进行；
确认时应能看到候选的完整依据（Learning Event、重叠度、场景分布）。
```

人工确认的结果记录为 Learning Reason，说明为什么新增或合并、依据哪些事件、适用哪些边界。

## 5. 执行语义

### 新增

确认后创建概念，归属指定 Domain。候选期间累积的观察（哪些知识点、哪些场景）转为该概念下的 candidate ActivationLink，进入正常的链接验证流程——新增概念不直接带来 verified 路径。

### 合并

合并 A、B 两个概念（并入 A 或新建 C），在一个事务内完成：

```text
ActivationLink 迁移：两概念下的链接改挂目标概念，
  场景 / 目标守门条件不变；
  同一 KnowledgePoint 同条件的重复链接去重，保留状态更高者
  （verified > candidate；weakened / deprecated 不因合并复活）；
KPP 挂载迁移到目标概念；
相关 Wiki 页面标记 needs_recompile，不自动重编译；
被合并概念不删除，标记 merged_into 指向目标概念。
```

`merged_into` 与 lifecycle 的 superseded 同一思想：数据保留，可追溯历史 Learning Event 和 Trace，但不再作为当前认知入口参与匹配。

### 拆分

反向操作：确认拆分方案后，原概念下的 ActivationLink 按场景 / 目标簇归属迁移到新概念，原概念视方案保留或标记 merged_into。

## 6. 与 preset 的关系

preset/domains.json 启动时 UPSERT 写入领域和概念。演化结果必须在 UPSERT 之后仍然成立：

```text
人工确认的新增、合并、拆分结果优先于 preset 重放；
被 merged_into 的概念不因 preset 中仍存在而恢复为当前入口；
preset 更新新增的概念正常写入，与演化产生的概念并存。
```

## 7. 边界

```text
不在导入期运行：导入只产生候选线索，不改概念结构；
不自动执行：Study 只提候选，不直接改结构；
不追求完整分类学：概念演化由使用信号驱动，
  没有信号的领域不需要主动整理概念；
Domain 层面的新增与合并使用同一套机制，但门槛更高、
  影响面更大，暂不展开，实现上推迟于概念演化。
```

## 8. 总结

概念演化让认知入口跟着使用生长：缺口反复出现的地方长出新概念，边界反复混淆的概念被合并或拆分。

一句话总结：

```text
候选来自 Learning Event 累积，晋升和合并由人工确认；
执行时链接、模式挂载和 Wiki 标记随概念迁移，
被合并的概念保留可追溯，但不再是当前入口。
```
