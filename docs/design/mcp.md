# MCP 能力（对接 AI Agent 平台）

MCP（Model Context Protocol）能力是知识大脑与外部 AI Agent 平台之间的接口层。它让 Agent 平台可以把知识大脑当作一个可调用的"外部记忆"来使用，而不需要理解知识大脑内部的检索分层、置信度收敛、Wiki 编译等机制。

## 1. 为什么只做两种能力

Agent 侧需要的只是两件事：**把材料放进来**、**把材料找出来**。中间的"怎么理解材料""怎么判断证据够不够""怎么组织成答案"，知识大脑内部已经有完整的机制（source_process/unit_extract、ActivationLink、Wiki 编译等），也已经有独立的判断标准，不需要因为多了一个 Agent 入口而重新设计一套。

因此 MCP 层的定位是**薄封装**：

```text
import_file  -> 复用现有 source_process/unit_extract 链路
retrieve     -> 复用现有 retrieval 检索链路，只返回原始证据
```

不做的事情，及其理由：

- **不做答案合成**：检索只返回证据（内容 + 来源），怎么组织成给用户看的答案，交给 Agent 平台自己的 LLM 去做。知识大脑不知道 Agent 平台的对话上下文、语气要求、目标受众，勉强合成答案反而是重复劳动。
- **不做结果反馈接口**（如 `report_outcome`）：知识大脑的学习闭环（ActivationLink 置信度收敛）依赖的是内部的 `fast_path_verify` 等自证机制，不依赖下游是否满意。Agent 平台不回传"这次答案有没有用"，不会拖累系统自身的学习循环。
- **不做导入状态轮询工具**：本系统定位是个人电脑上的知识管理系统，文档处理耗时通常在数十秒量级，`import_file` 内部有限等待即可覆盖典型场景，不需要额外一个工具专门查状态。
- **不做行级坐标+颜色高亮的跳转链接**：这是编辑器专属能力（如 VS Code 的 `line:col` 跳转），不同 Agent 平台底层用什么工具打开文件不可控。改用 Markdown 标题锚点（`file://...#标题slug`），这是跨工具通用的定位粒度，牺牲的是"精确到具体某几行"，换来的是"大多数本地工具都打得开"。

## 2. 为什么导入要同时支持路径和内容两种输入

本系统运行在个人电脑上，AI Agent 平台也运行在本机或能访问本机文件系统，这是"直接传本地文件路径"能成立的前提——不需要把文件内容搬运一遍，效率最高。

但并非所有要导入的材料都已经落盘。典型场景是 Agent 生成的内容（例如帮用户整理的一段结论、一次任务执行的复盘）本身只存在于对话/生成结果里，没有对应的本地文件路径。这种材料如果只支持路径导入，会被挡在门外；如果只支持内容导入，则本地已有文件要多一次不必要的读取+编码。

所以两种输入方式不是二选一的偏好，而是覆盖两种本质不同的材料来源：

```text
文件已在本地磁盘   -> 传路径，读取效率最高，无编码开销
材料只存在于 Agent 侧、未落盘 -> 传内容（base64），没有第二种办法
```

至于哪种情况用哪种输入，由 Agent 自己根据材料的实际存在形式决定，知识大脑不做限制、不猜测。

## 3. 为什么检索结果里的来源要解析成人类可读的引用

`retrieval` 内部的 `Evidence.SourceRef` 是 `{source_id, line_start, line_end}`，这是系统内部坐标，不是给人看的。如果原样透传给 Agent 平台：

- Agent 平台的 LLM 不理解这个坐标的含义，也没有能力/没有必要再反过来调用知识大脑的其他接口（如大纲查询）去拼出"这是哪个文档的哪一章"；
- 即便去拼，每条证据都要一次额外的接口往返，检索延迟会明显变差。

所以引用解析（source_id + line 区间 -> 文档标题 + 命中章节标题 + 本地文件锚点链接）放在 MCP 层内部完成，返回给 Agent 的每条证据自带一份"读得懂、点得开"的引用，不需要 Agent 自己再拼装。

## 4. 覆盖范围与后续演进

当前只覆盖"文件导入"和"知识检索"两种能力。会话过程中讨论过的"Agent 生成内容自动沉淀为记忆并在相关话题中被动召回"这类诉求，受限于 MCP 协议本身是请求-响应模型（Agent 的 LLM 决定要不要调用工具，知识大脑无法主动推送），不属于 MCP 层能解决的问题，需要依赖 Agent 平台自身的工具调用策略（例如每轮对话都尝试调用 `retrieve`），不在本次设计范围内。
